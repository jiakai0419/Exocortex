# Bounded remote sample in the existing worker

Candidate design, 2026-10-05. This is not a deployment or evidence about any real account. All fixtures are newly synthetic. The production checkout and remote business records remain untouched.

## Outcome and integration

After a successful existing worker cycle, one due hook starts a bounded diagnostic child without waiting for its API calls. The next sync cycle can proceed while that child runs. No second daemon, external automation, or business-data repair is introduced. `status` reads a redacted cache only; `check --live` uses the same sample collector. A sample is evidence about the stated messages and time window, never full-history completeness or client rendering equality.

Manual checks have two execution boundaries: no-cache checks use the guarded one-shot collector, and cache-writing checks use the shared scheduler. Test fixtures replace those same boundaries and return the current v3 report; they must not select a separate legacy collector or cache writer. A failed collector and a not-due scheduler remain visible through the public command. Legacy v1/v2 cache files remain readable for compatibility, but new attempts only publish v3 through the existing guarded paths. The former hot-chat collector, ID-only report and v2 writer are retired after their pagination, malformed-evidence, privacy and read-only counterexamples are covered by the current sampler.

Engineering defaults (not API guarantees): 15-minute cadence, 30-minute cache lifetime, 10-minute stability buffer, preceding 24-hour creation window. The endpoint's create-time window cannot discover edits to older messages. Cadence may be disabled or set from 15 to 30 minutes; TTL is twice cadence, at most one hour. Cache age, last attempt, scope, counts, inconclusive reasons and unsupported comparisons remain explicit.

## Sampling and conclusions

Use the already-discovered local enabled received-chat inventory: two recently discovered hot-ranked chats plus three chats rotated in stable identifier order. When retained historical observations exist, one rotating slot may revisit one exact historical creation-time window, preserving two hot and two ordinary fair slots. This deliberately avoids another remote directory scan and undocumented shortcut HTTP fanout. Undiscovered/disabled/muted/inaccessible chats, unobserved older messages, thread-container-only replies and client-only dynamic rendering are outside the claim. Persist only the numeric rotation; refresh candidates every run. The inventory can change, so fairness describes rotation through each observed inventory, not guaranteed global coverage.

For each selected chat request at most two native message-list pages of 20 items. Freeze the time window, sort and container for pagination; validate envelopes, IDs, chat, timestamps, page sizes and token progression. A truncated page sequence is reported as a bounded partial sample, not complete window coverage. Empty, errored, unbound and interrupted samples cannot become a positive signal.

Compare ID/source/type/container first. Coverage history, detail debt and candidate records are read in one read-only SQLite transaction; revocation/deletion cannot combine an old coverage proof with a new absence. A missing record whose scope has not successfully covered the message's creation time remains pending synchronization. A successful coverage interval must come from the project's sole coverage implementation, not a cursor maximum or arbitrary worker success. Retain a bounded, private hash-keyed observation (DB/account/message/target) for a suspect; confirmation requires the same remote observation and a later successful interval covering that same target after the first observation. Retired run evidence and missing detail closure remain unverified. Unrevisited suspects remain unresolved and do not silently disappear into a healthy result.

Compare versions only when timestamps and native source semantics are usable. Detect explicit native identity, message-type and retraction contradictions. Compare static text/post API body JSON with canonical object-key ordering, retaining array order. Exclude sender names, renderer output and full raw-record hashes. Dynamic cards, merged forwards, legacy source shapes and unavailable versions explicitly count as content unverified. A newer local version is a race/unverified result. A newer remote version or same-version native static-body difference is a candidate discrepancy, not a claim that the client presentation was lost.

## Account binding and concurrency

An authenticated `open_id` alone does not prove DB ownership. Local evidence must either be a matching persisted binding from an initially empty DB whose list/discovery commit confirmed its account association, or explicit, single, nonconflicting sent-self history matching the current principal. A pending source reservation constrains write admission but supplies no positive sampling evidence. Unknown/mixed/mismatched identity fails closed. The evidence source is reported; this is account association evidence, not proof that every historical record belongs to one account. The sampler does not adopt an old DB, change permissions, or broaden OAuth scopes. Re-read identity and DB file context before accepting a result. A verified account/database namespace change invalidates the old observations/cache; an unverified alternate account cannot erase prior namespace debt.

Sync and diagnostic API reads cooperate through one local process lease. Worker sync runs first. Foreground sync retries a busy lease for at most five seconds; it cannot preempt a request already in flight. The probe only tries the lease per request, never waits for it, never sleeps with it held and releases it in `finally`. A request has a four-second timeout. Busy cancels the partial sample. The diagnostic lease is never held for the whole 60-second child. A kernel flock releases on the final close, including process death; unsafe lock files fail closed. The held descriptor is inherited by an in-flight API subprocess, so killing its Node parent cannot prematurely release the request lock. One absolute five-second sync deadline bounds all acquisition attempts and helpers. This does not coordinate external clients or unrelated programs.

## Budgets, persistence and failure

At most twelve direct API invocations: two identity reads and ten message pages. A one-second minimum unleased gap after each diagnostic request is an application budget, not a separate official API quota. The entire collection shares a 55-second deadline, including request waits, pages and remaining-time SQLite budgets; scheduled and one-shot children both have a 60-second kill deadline. No in-run remote retries. Honor returned rate-limit reset durations; carry cooldown to later attempts and prevent diagnostic calls during known sync cooldown. Private UID-wide immutable operation cooldown records propagate known resets across cooperating worker, foreground sync, manual probe and database paths; corrupt evidence fails closed. Do not invent an undocumented identity endpoint rate threshold.

One atomically replaced private scheduler state stores due time, attempt state, capped exponential failure backoff (15 minutes to six hours), rotation and at most 200 hash observations. Seven days marks stale evidence rather than deleting unresolved observations. Overflow retains a sticky debt marker; forgetting omitted identities cannot certify a later healthy sample. Reserve the next attempt under flock before any API request so a crash/restart after reservation does not create immediate request storms. A separate POSIX flock lease scoped to the shared cache destination prevents concurrent worker/manual cache-writing checks, including different database identities using one log directory. Such manual checks share rotation, prior observations and due/backoff; not-due is explicit incomplete without a fresh API call. No-cache one-shot checks do not confirm or clear prior scheduled observations. A failed/busy attempt never renews an earlier success. Cache/state parse, future-time, DB/account mismatch and schema-policy errors fail closed. Evidence readers open with O_NONBLOCK and O_NOFOLLOW, validate private same-user regular files with one link, read through the opened descriptor, and reject metadata/path changes. All sample counters are bounded and cross-checked before normalization; a malformed count cannot become a positive signal. Schedule state and the unavailable attempt marker fsync both file and parent directory. Prepared cache publication follows the ephemeral final-rename contract in [Remote sample process lifetime](remote-sample-lifecycle.md); the worker never publishes positive evidence before guardian cleanup. Persisted files use 0600 and no IDs, names, links, bodies, raw CLI output or errors in public cache/log events.

## Official API references

Verified 2026-10-05 against [message list](https://open.feishu.cn/document/server-docs/im-v1/message/list), [user info](https://open.feishu.cn/document/server-docs/authentication-management/login-state-management/get) and [frequency control](https://open.feishu.cn/document/server-docs/api-call-guide/frequency-control).

- Message list documents page size 1–50, second-resolution start/end, create-time sorting, and 1000/minute plus 50/second limits. Those are documented endpoint limits at verification time, not our polling defaults or an SLA. Thread containers require distinct requests and do not support the same time filter; the sample does not claim to enumerate all replies.
- The documented card content selector is `user_card_content`. Older code uses `raw_card_content`, which this public endpoint document does not establish. The probe uses the documented selector and never compares dynamic card body representations.
- User info requires the current user token and returns application-scoped `open_id` and `tenant_key`. Its frequency tier is Special; no numerical threshold is assumed. Authentication failures remain diagnostic unavailability.
- Limits are generally scoped by API/app/tenant, shared with sync. HTTP 429 (or legacy 400), code 99991400 and `x-ogw-ratelimit-reset` indicate throttling; reset is a number of seconds to wait, not epoch time. Missing headers use the conservative local failure backoff. CLI shortcuts can hide multiple HTTP requests, hence the direct endpoints above.

## Implementation/review notes

The API lease uses one never-unlinked private UID-wide regular file. A short Python helper applies nonblocking flock to a duplicate of Node's descriptor; the shared open-file description retains the lock after the helper exits. This removes PID inspection, process claims and stale-owner recovery. This behavior was tested on the local macOS host using synthetic files: helper exit retains ownership, final close releases, and process crash releases once inherited request descriptors close. See [Apple flock documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html). The scheduler uses one separate cache-destination flock: an outer wrapper acquires it, execs the guardian in the same PID, and the guardian retains it through final publication or skip. The anchor and worker inherit the descriptor; the worker does not own the lock lifetime. While holding this lock, the guardian rechecks the latest due timestamp before writing an attempting marker. A short-lived guardian enforces a monotonic 60-second deadline, notices worker death, and terminates the probe process group even when the worker's synchronous event loop is busy; it has no scheduling loop or durable state of its own. The worker owns only one in-flight job. Both normal worker exit and sync exceptions stop it. A finite `--once`/max-cycle run cancels an unfinished diagnostic during cleanup; it does not wait for sampling. A persistent worker is the intended periodic host. Parent-exit detection is polled every 50ms by the guardian; the independent monotonic deadline still bounds the whole process group. The account sidecar is `<canonical-db>.remote-account-binding.json`, stores only hashes/time, and is ignored by Git. File-cache context retains the existing local diagnostics fingerprint for compatibility; account/observation state uses the stronger activity fingerprint including file birth identity. Both are checked again after collection.

A native API mismatch is evidence about the source payload. Dynamic card contents and client rendering remain unverified even when `update_time` matches. Undocumented `only_thread_root_messages` is not used. Rate documentation can change; the one-second local gap and twelve-call cap deliberately do not claim an independent official allowance.


## Root-review regression acceptance

The candidate must pass each reported counterexample, in addition to the general suite:

1. Actual `writeLog` → event reader → service/public report accepts only the explicit versioned schedule-event contract. Unknown fields and invalid outcome/reason pairs fail closed; schedule start does not manufacture sync activity or statistics.
2. A synthetic WAL writer atomically revokes coverage and deletes a record between reads. A single reader snapshot sees either the old proof plus record or the new absence without proof, never false confirmed missing.
3. Numeric, object, array, boolean, null and blank native message/chat IDs cannot be equal, healthy or sampled.
4. Account-binding and v3-cache files with 0666 mode or multiple hardlinks are rejected without chmod. Future/noncanonical binding time, symlink, FIFO and mid-read replacement are rejected. Binding publication fsyncs both file and directory.
5. Hot/fair/eligible/truncated counts obey selection and pagination relations; every current finding is bounded by the sample, historical counts by the 200-observation state. Failed samples retain valid partial counters but cannot bypass these checks. Direct summary projection also validates before displaying evidence.
6. A real synthetic FIFO state path returns invalid in an isolated two-second-bound child; worker sync still proceeds. A blocked fake probe cannot delay the next sync. Guardian termination covers worker exit, exception, deadline and descendants.
7. Repeated synthetic 1900ms lease attempts share one absolute five-second budget and the last attempt receives only the remaining time. These clock-injected deadline regressions are distinct from actual local OS flock ownership tests. Ordinary sync has no `ps` dependency.

No real account/API, production LaunchAgent, or deployed lifecycle validation is claimed. Those remain the independent production integration gate.


## Second root-review correction

Both manual execution paths (cache-writing and no-cache checks) must run through the same short-lived guardian as the periodic worker. The guardian owns the process-group deadline and cleanup, including a CLI descendant retaining the API flock; a timeout must never kill only the Node leader and leave that descendant running. The synchronous caller waits for the guardian to finish cleanup before accepting output or reporting failure. The inner process-group deadline is 60 seconds; the synchronous outer backstop is 62 seconds with SIGTERM, leaving two seconds for cleanup rather than killing the guardian with SIGKILL. Guardian session isolation also lets it clean up after a terminal SIGHUP terminates the caller. Regression acceptance invokes both actual public helper paths with a synthetic child/grandchild, then verifies descendant exit and lease reacquisition after timeout.

The five-second foreground lease budget and each helper's remaining timeout must use one monotonic clock. Wall time remains for durable due/cooldown timestamps, but clock adjustments cannot increase an in-process wait budget. A synthetic test moves the injected wall clock backward by ten seconds while monotonic elapsed time advances; total helper work plus sleeps must still fit five seconds. No machine-clock change is needed or permitted for the test.


## Safe guardian failure diagnosis (isolated candidate)

The guardian emits only a versioned `guardian_diagnostic` with a first primary error and a first cleanup error, each limited to a fixed stage and an integer errno (or null). Raw exception strings, stack traces, paths, process identifiers, arguments, environment values and child output do not enter this diagnostic. The two errors remain distinct so a cleanup failure cannot erase the original failure. No permission error triggers a retry, alternate interpreter, alternate watcher or relaxed process-group cleanup. Reaping after successful termination is bounded; if termination fails and exit was not observed, the guardian does not wait indefinitely.

When no earlier primary error exists, a DONE frame confirming nonzero worker exit, excluding the reserved cache-mode skip code 3, supplies primary `child_exit` evidence even when cleanup also fails. The subsequent bounded wait reaps the anchor, not the already-observed worker. An anchor reap timeout leaves anchor exit unknown without erasing a confirmed DONE result. A confirmed anchor exit other than its expected SIGKILL supplies `anchor_lost` independently of another cleanup failure; an unknown anchor return code does not establish `anchor_lost`. The first cleanup failure remains independently available.

The synchronous wrapper validates this structure and manual cache-writing/no-cache checks preserve it through the public report projection. A diagnostic is failure evidence and cannot accompany a healthy result. This small candidate does not add a new background diagnostics file or connect ignored background stderr to worker logs; background guardian-stage persistence remains unimplemented.

If the output channel itself fails, the guardian does not retry publication; the caller may only retain the generic `guardian_result` fallback, without the original publication errno. These stage codes identify where the observed failure occurred; they do not establish whether sandbox, TCC, or another host policy caused it.

The initial diagnostic iteration was validated with static build/type/syntax/generated checks and mock-only unit tests. Its Python test harness replaces every guardian OS/process module before executing the state machine; it never starts a child, opens kqueue, signals a process, reads a business database, calls an API or queries system logs. The earlier deferral of full verification is historical: the separate bounded synthetic OS matrix and complete verification have since passed, as recorded in [Remote sample process lifetime](remote-sample-lifecycle.md#acceptance-boundary). Runtime evidence and user-run diagnostic scripts remain outside Git.

## Bounded coverage query planning

The retained-run query for one sample target must filter by that target's scope without scanning successful history from unrelated scopes. Both the scope/start-time and status/start-time indexes exist in the application schema. With both available, SQLite can choose the status index and exhaust the shared inspection deadline before records can be compared; a result-row limit does not bound rows visited before filtering. The generated coverage fixtures therefore include both competing index shapes.

This one query uses `+r.status = 'succeeded'` to disqualify the status predicate from index selection while preserving the scope predicate. [SQLite documents unary `+` as a query-planning workaround](https://www.sqlite.org/optoverview.html#disqualifying_where_clause_terms_using_unary_); it also removes type affinity. Here `status` is a TEXT column compared with the fixed nonnumeric text `succeeded`, so the exact accepted status is unchanged. Synthetic counterexamples reject null, numeric, blob, failed and differently cased status values. No index name is required, and databases without the scope index still execute the query under the existing deadline.

This is a local read-only workaround, not a migration or statistics update. It does not run `ANALYZE`, add an index, change SQLite data, extend the 3.5-second inspection budget or five-second subprocess bound, change target/run/record limits, or weaken the exact window, cursor, chronology and detail-completion checks. The regression generates 20,000 successful runs in another scope and applies a fixed 10,000-instruction SQLite VM budget: the old query is interrupted, while the scoped query proves the target's coverage. Existing per-target, total-run, deadline, invalid-evidence and atomic snapshot counterexamples remain required.


## Collector failure evidence

A valid unavailable v3 cache can carry `reason: invalid_evidence` from the collector itself; that reason alone does not establish that cache parsing failed. Before stage diagnostics, identical counters could result from a rejected later message page or from a local snapshot failure after the final identity request. Historical caches cannot reconstruct the lost exception stage or the exact remote target set. Reproducing a local snapshot failure is useful evidence but does not uniquely prove the cause of every earlier remote attempt.

The collector now adds optional `collector_diagnostic: {version: 1, stage, code}` for caught non-`SampleFailure` exceptions. The contract accepts exactly those three fields with fixed stage/code pairs. The stage distinguishes inventory, before/after identity and binding, message requests, native page schema, raw-message shape, message identity, database context, snapshot, comparison and final context. Snapshot codes distinguish target/budget validation, missing dependency, timeout, other process signal or execution failure, JSON/output schema, coverage invariant, record schema/size, and the Python reader's explicit inspection-budget or read failure. Typed SQLite failures preserve only their four fixed categories. Unknown exceptions become fixed error categories; no exception message, stack, errno, path, identifier, response, SQL or body is copied.

`collector_diagnostic` is separate from guardian lifecycle evidence. It does not change scheduling, API calls, request/inspection limits, observations, rotation, account binding, or comparisons. The original failure remains unavailable and cannot renew success. Cache/report schema v3 remains compatible with older caches without this optional field; a present invalid diagnostic or success contradiction is rejected by raw cache validation. Public projection and live checks cannot strip a present diagnostic into a healthy result. Status JSON retains the safe diagnostic; `status --detail` and manual check text show its fixed stage/code. Expiry and database-context rejection keep their existing precedence, and normal status stays compact.

Offline acceptance includes two complete synthetic collector paths with the same request/page/chat counters and distinct page-versus-snapshot diagnostics; explicit budget/read/process failures; message-shape and comparison errors; unchanged failed-attempt rotation and previous observations; bounded lease release; old-cache compatibility; malformed and contradictory diagnostics; narrow terminal layout; and privacy markers. No real remote payload is used as a fixture. Deployment and a later naturally scheduled production attempt remain separate acceptance gates.

## Retained historical observations

A retained observation may carry a salted scope hash and a last-attempt time, never a raw routing ID. Each run resolves its route against current enabled scopes and the verified database/account namespace. Legacy entries without a scope hash use a bounded exact-creation-time local lookup only when the message hash maps uniquely. Ambiguous, absent or oversized results remain unresolved. The narrow historical window spans three seconds and at most two pages; the same twelve-call, 55-second collector and 60-second guardian limits cover both current and historical slots. Current synchronization keeps its lease priority and shared cooldowns.

Coverage compares the expected chat identity and enabled source/scope in the same read-only SQLite snapshot as records. An actual failed historical request may advance only the existing target's attempt-order timestamp, after strong database/account/source checks; it cannot refresh evidence age or remove debt. Unverified alternate accounts preserve the previous account's observations and overflow together. Only successful verified namespace changes can replace that ownership. Cache publication rollback restores this state together, and public projection, cache parsing and live-check success use the same historical metadata validity rules.

Matching an eligible fresh response closes that retained observation; absent, truncated, restricted or unroutable results do not. Static content is compared where supported; matching a card's API version does not prove its client interaction state. The existing explicitly reviewed replay remains the repair path. No-cache live checks do not clear scheduled observations, and manual cache-writing checks obey the existing due gate. Operators must distinguish exact repair verification from later natural cache closure and must not edit schedule state to accelerate acceptance. This mechanism does not sweep unobserved historical edits or alter synchronization cursors.
