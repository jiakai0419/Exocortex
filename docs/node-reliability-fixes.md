# Node reliability fixes

> Historical implementation and regression record for the reliability candidates before CLI v2. Counterexamples remain relevant; command names, lifecycle recipes and test counts below describe those candidates, not current acceptance. Current commands and changed defaults are documented in [Operations](operations.md), [CLI migration](cli-migration.md) and [the command catalog](commands.md).

## Scope and implementation plan

This change covers three reliability fixes on the existing Node implementation, plus the explicitly scoped status and card-reading follow-ups below.

1. Isolate merged-message detail failures from conversation availability. Preserve ordinary messages, represent missing details, and keep them retryable. Split oversized native windows after bounded timeout, with explicit limits; incomplete windows must never advance a cursor.
2. Make service lifecycle results reflect launchd outcomes. Distinguish an absent job from an inspection failure and propagate start failures. Require fresh activity evidence before reporting active synchronization, including independent foreground synchronization.
3. Use one merge policy for synchronization and enrichment. An unknown name lookup must preserve a known name; an explicit authoritative clear must remain expressible. Same-version projection improvements remain valid and idempotent.
4. Clarify retained-log timing, chat-list review and active refresh semantics, and abnormal lease evidence without introducing new discovery counters.
5. Read stored cards through one bounded text projection, preserving old-record data and existing JSON fields while improving multiline human output.

## Acceptance plan

- Use only newly invented messages, identities, clock values, subprocess results, and temporary databases. Do not derive fixtures from operational data.
- Retain regression cases for each reported failure and counterexamples that define the limits of each fix.
- Run focused tests while implementing, then the repository's build, typecheck, syntax checks, full test suite, and generated-file consistency check.
- Document exact pass/fail/not-run outcomes and the remaining operational validation boundary.
- Keep runtime entry points stable. No rewrite, deployment, service lifecycle operation against a real service, or production data mutation is part of this work.

## Implemented contracts

### Incomplete details and bounded progress

Normal synchronization now separates list coverage from complete content. `fetchChatMessageList` / `fetchSentMessageList` finish every list/search/mget page before returning ordinary messages and raw merged roots. Migration 009 adds a durable list checkpoint and per-root detail tasks. A fenced transaction commits ordinary records, queued roots, and the next list checkpoint together. Partial list pagination commits none of these. The complete-content cursor stays unchanged while any root is pending, so ordinary messages beyond a denied root remain ingestible across shrinking windows and process restarts without claiming full coverage.

Detail retries use a separate run and the root fingerprint as a compare-and-swap condition. Each successful listing attempts at most five due roots under one shared 30-second request deadline, so several healthy roots can complete without increasing the previous worst-case request budget; `--scope details` independently retries a bounded batch (default 5, maximum 20) without any list request. The batch shares a 30-second request deadline; each root has at most 50 pages, 1000 items, and 64 tree levels. Failures remain pending with exponential backoff from 60 seconds up to 24 hours. Locked scopes are refilled within a finite candidate scan of `max(3×limit, limit+20)`; scopes beyond that bound can be deferred under sustained contention. Completed receipts are updated to the authoritative refreshed root and prevent unchanged inclusive-boundary roots reopening debt. Identical repeated roots from completed pages are deduplicated; conflicting same-ID evidence rejects the list transaction. The authoritative current root may be a newer source version; identity changes, regressions, same-version conflicts, and missing expansion remain incomplete. Failed refreshes retain any previously stored complete root.

Only after every task is complete does the storage transaction promote the full cursor to the continuous list frontier and emit a composed coverage interval. Partial runs contain `list_window_*`, `list_complete: true`, `details_complete: false`, and `window_complete: false`, never successful interval keys. Status, service readiness, and coverage diagnostics consider current detail debt even when historical successful runs or old health values exist. Read-only legacy diagnostics explicitly distinguish unavailable old-schema evidence from a damaged upgraded database.

`MessageWindowBudgetError` still identifies exhaustion of the shared 180-second native list deadline. The runner then retries the smallest minute-aligned prefix once; page-cap failures retain their bounded bisection behavior. Ordinary request timeouts, rate limiting, malformed responses, and permission errors do not justify shrinking. Detail limits never trigger list bisection. A saturated minimum prefix remains a safe failure. Strict fetch APIs used by bounded replay still require the complete content window.

The initial candidate saved ordinary messages only inside its repeatedly retried prefix. Independent review found that a denied root plus window shrinking could starve later ordinary messages, despite passing its original tests. That candidate is retained unchanged for comparison. This follow-up replaces that insufficient progress contract rather than claiming that all detail failures previously blocked every list shape.

### Truthful lifecycle and activity

launchd inspection returns loaded, absent, or unknown. Absence requires both exit status 113 and the service-not-found diagnostic; permission/domain/spawn/signal errors remain unknown. Start and install propagate kickstart failure; `start requested` confirms command acceptance only. Stop verifies absence before success; uninstall retains the plist if verification fails.

Completed worker-step events are historical facts. Current Activity requires a database-bound phase, matching OS process-start identity, liveness and a finite phase validity interval; a lease alone establishes only mutual exclusion. Worker cycle gaps, active steps, scheduled waits and exits are explicit. Foreground sync can be active while launchd is stopped, but without a hard command deadline only a short observation window is claimed. Invalid, expired, ambiguous or unavailable evidence remains unknown. Database-only sync-status and doctor never promote old running rows or reservations to current syncing. See [Activity evidence](activity-evidence.md) for the state matrix, process-observation limits and restart requirements. `wait-ok` still rejects unfinished cycle history, failed status subprocesses and pending detail debt.

### Consistent health evidence

All database facts used by the status report—detail debt, list progress, records, scopes, discovery, runs, and locks—are read by one SQLite SELECT inside one read-only transaction. Schema preflight chooses the query shape only; the final snapshot rechecks that shape and migration 009. Concurrent schema changes, missing sections, or unparseable evidence reject the report; invalid aggregate counts remain unavailable and require attention instead of becoming zero debt or legacy evidence. Service health and `wait-ok` consume that consistent report.

A report describes one database snapshot. A writer may commit after the snapshot begins, so a coherent earlier report remains possible; it cannot combine earlier zero debt with a newer incomplete list frontier or failed run. Synthetic WAL tests keep a real reader transaction open while a separate process commits through the real synchronization adapter and store, then verify both the complete earlier report and the incomplete subsequent report. The earlier `b528dc6` candidate is retained in Git history as the negative comparison; this correction is an appended commit.

### Status timing and concise explanations

The longest success interval now measures only adjacent observed successful cycles inside the requested window. Neither window edges nor time since the last success contributes to it; fewer than two successes yields `null`. The last-success age remains separate. Observation metadata describes the retained current-log range, clipped to the requested window, with explicit tail truncation and unknown-range cases. It never claims service startup or continuous coverage. Exact milliseconds remain available in JSON; only the gap's terminal display rounds to a second.

The existing service layout remains: Chat list review shows its recorded completion time instead of leading with page counts; Active chat refresh shows its last successful refresh time. Both default to the API list of non-muted group and private chats, not an unbounded all-conversations claim or proof of complete messages. Existing received-scope counts retain their distinct meaning. Normal lease occupancy is not current Activity evidence; only timestamp-supported lease anomalies produce a warning. No waiting or process-liveness claim is inferred from a lock alone. Technical cursor and lease fields remain in detailed diagnostics, and no new discovery-count storage mechanism is introduced.

### Shared name merging

The Lark-specific SQL merge is shared by ingestion and enrichment. Null/empty lookup results mean unknown; explicit `*_name_state: "cleared"` is authoritative. Known names and provenance remain together only when record and canonical identities agree, including the container for scoped sender names. Unknown cannot resurrect a cleared name; a fresh resolved value may replace a clear. Cached chat names explicitly carry `scope_config` / `local_history` provenance and can only fill unknown fields; they cannot overwrite a known name or authoritative clear. A fresh message name remains eligible for a same-version improvement. Other record types keep their existing replacement semantics.

Ingestion applies the merge within its transaction before calculating actual write effects. Enrichment applies the same expression to its snapshot and commits only under the existing exact comparison and maintenance fence. Equivalent typed JSON projections retain stored bytes so property ordering does not create spurious updates. Same-version projection improvements remain allowed; older source versions cannot replace newer records. The helper explicitly materializes intermediate SQLite results to prevent exponential expression expansion.

Sender identity is now explicit: raw typed evidence and `canonical.sender_id_type` must agree with the actor before names enter a lookup or cross-record merge. Same-text IDs in different namespaces cannot inherit names. Legacy prefix inference is limited to local merge compatibility; it does not authorize an API query. Online ingestion and both enrichment modes share contact/member normalization, 30-ID request batches, localized names and self-seed priority. ID echoes, conflicting results and failed lookups remain unknown.

Historical repair has an explicit `--sender-only --sender-id <open_id>` mode. It selects missing names for one validated actor before LIMIT (default 50, maximum 100), keeps a 30-second remote deadline, and caps member fallback at three chats and five pages. Dry-run exposes unresolved or additional candidates without writing. Real updates use the shared merge and snapshot CAS, preserving raw/hash/source version/body; the ordinary recent-record enrichment mode retains its separate scanning semantics. See the [shared design](card-and-identity-projection.md) for the exact budget, provenance and failure contract.

### Bounded card reading

The [card and identity projection design](card-and-identity-projection.md) defines the shared namespace, content, diagnostic and resource contracts before implementation; its module table records the completed responsibilities and their boundaries.

Native interactive messages and read-only historical views share the same limited card parser. It reads the outer payload and nested `json_card`, then projects known title, text, field, layout and navigation-button nodes. Version 3 preserves `br` nodes and block boundaries as line breaks while keeping inline nodes and meaningful trailing text in source order. It accepts the explicit native `link.url = {url: string}` wrapper and collapses action buttons that explicitly have no usable navigation link; safe HTTP(S) navigation remains visible, and complete button data remains in raw. Hiding a button does not imply that its action completed. Nonempty invalid URL values, unknown visible structures, malformed payloads and resource limits retain their explicit diagnostics; no callback is executed and no network request is made.

Mentions require exact, unambiguous evidence from the same message. Besides direct `mentions` identities, the parser resolves native references through the outer `json_attachment.at_users` mapping: an own dictionary key of `at_users` or an entry's `user_id` links to its `mention_key`, then to that message's `mentions` name. Missing or conflicting mappings stay unknown; order, identifier prefixes, other messages, caches and online lookup do not supply identities. If unresolved mentions are the only missing content, their inline placeholders suffice for human output; JSON still reports `partial` with `unresolved_card_mention`, without an additional generic full-line marker. Other critical omissions still produce their own explanation. Input parsing, traversal and output remain bounded, and terminal controls are removed before multiline indentation.

Historical reads leave stored body, raw, canonical, hashes and source versions unchanged. Existing JSON fields, including `display.body`, retain their meanings; optional `display.card` adds the current projection and its status/version. The human view always uses that card result and never falls back to dumping unsupported raw JSON. Newly ingested cards can improve their derived projection while retaining source evidence and same-version idempotency. Links display only HTTP(S) origin/path with explicit omission of credentials, query and fragment; original URLs remain private raw data. Search still filters stored body. See the [operational contract](operations.md#卡片阅读与原始数据契约) for limits and compatibility details.

Independent review of the first card candidate found four gaps despite its 685 passing tests. The follow-up explicitly projects header subtitles, container extras and platform URLs; it marks unsupported shapes incomplete. URL tokens are consumed before projection, including IPv6 and brackets in query data, and generated display markers are kept separate from raw token recognition. Control-sequence stripping is a linear scan. Mention expansion charges a bounded workspace during substitution and caches the name projection, preventing a multiplicative intermediate allocation. Full-strength regressions retain 245,000 unterminated OSC introducers and 10,000 mentions of a 16,384-character name, each in a subprocess with a four-second deadline, 64 MiB V8 heap and peak-RSS assertion.

A subsequent review found that the Markdown-first pass could still split a bare IPv6 URL when an unrelated Markdown link followed it, exposing query text. One forward lexer now recognizes complete URL atoms before Markdown at every source offset, including inside labels. Atom contents never become syntax; each destination scan consumes all examined input, and generated fragments are never scanned again. Ambiguous swallowed label delimiters remain explicitly partial. Sticky scheme recognition has a fixed bound, delimiter scans and atom scans consume disjoint source ranges, and input budgets cap their workspace. Raw text and names are accepted whole or rejected on input-budget exhaustion; cutting a value before URL parsing could otherwise turn credential text into an apparent hostname. If external name expansion exhausts its source-character budget, a fixed terminal placeholder is appended without rewriting or joining source fragments. Only final safe text is output-truncated. Control cleanup can also change URL boundaries, erase a scheme, or create one. A text value containing both dangerous controls and link syntax (before or after cleanup) is therefore explicitly rejected as a whole; adjacent nodes remain readable. Direct URL slots containing those controls are rejected. Control-only prose and ordinary whitespace keep their cleanup behavior. Original-strength OSC and mention resource counterexamples remain unchanged; the mixed control/hidden-URL fixture now asserts the explicit unsupported contract, with a control-only variant retaining its exact multiline assertion.

A further composition review found that replacing mentions before lexing could insert a space into an original URL query and expose its tail. The projection now tokenizes only original source offsets: complete URL atoms, control spans and Markdown destinations are consumed before mention resolution. Only external source mentions resolve; their independently cached name projection disables recursive mentions and is appended as terminal output. Neither names nor link markers are inserted into the source or scanned by the parent. A shared control-span scanner preserves hidden payloads across mention and Markdown boundaries, including a control sequence that outlives an inline tag. Identity matching uses the original identifier bytes. URL-internal tokens never invoke name lookup or expansion accounting. These rules apply identically to stored-card reading and newly normalized records.

### Card state freshness boundary

Card reading reconstructs a stored snapshot; it does not synchronize approval state. Normal list synchronization advances by message creation time, so a later `update_time` on an older card does not bring it back into the window. Ordinary interactive cards do not enter the merged-message detail queue. No card-state polling or real-time approval guarantee is introduced by this projection change.

A state mismatch first requires comparing the local raw presentation fields with `display.card`. An authorized, single-message read using the same identity and raw-card mode can then compare GET/mget evidence with the stored source version and content. Fresh API data differing from local raw supports a stale-snapshot diagnosis; unchanged API data with a different client view does not establish a parser defect. Endpoint or viewer differences remain possible until verified. Existing bounded replay reads the received list endpoint and only replaces strictly older numeric versions, so neither a different GET response nor a same-version conflict guarantees that replay will refresh the card.

A limited single-message diagnostic used one GET and one mget with the same identity. Both succeeded and returned card content structurally matching local raw; neither API snapshot supplied the processed state visible in the client. This observation does not establish an omitted parser field, universal endpoint behavior, or real-time state support. Source-version comparison remains separate from content comparison; different timestamp representations alone are insufficient evidence of a newer card. The diagnostic performed no record update or deployment.

### Review follow-up: projection and current-evidence boundaries

Independent review rejected the first identity/activity candidate despite 1019 passing tests. Four newly invented counterexamples exposed incomplete phase-event validation, an unrelated orphan child suppressing verified foreground activity, an empty primary URL hiding a usable fallback, and fields running into a following inline content slot. The original candidate and its test evidence remain retained; its pass count is not acceptance of this follow-up.

Activity event shape is a shared reader/selection/evaluation contract, so a parseable but incomplete activity event cannot resurrect an older phase. Child processes are classified by instance association before evidence is prioritized: an invalid child never becomes independent foreground evidence, while another verified independent foreground phase can establish current synchronization. Container slots retain block boundaries while content inside one inline slot stays continuous. Navigation normalizes supported empty target forms before selecting the next explicit slot; nonempty invalid targets retain their diagnostic. These rules apply to native projection and read-only historical display, with same-version correction remaining idempotent.

The sender follow-up defines a finite compatibility-input contract instead of claiming every shape is returned by the current API. Record creation, source-name checks and enrichment use one scalar actor selection and complete explicit-ID alias set; SQL mirrors the finite source slots and selection order. Direct/nested user and union IDs retain valid source names without becoming open-ID query targets. Malformed identity objects cannot become actors. Names echoing any known source alias remain unknown across direct names, remote results, existing projections and repair selection, so an alias cannot suppress a legitimate member fallback or count as resolved.

### Review follow-up: uncertainty and newly learned identities

A second independent review closed the original four counterexamples but rejected two remaining compositions despite 1164 passing tests. A suspended or uninspectable worker parent lost its association and let a child masquerade as independent foreground work. A newer source version supplied an additional typed ID equal to the old displayed name; the new record correctly classified it unknown, but the merge restored the old ID string using only previous-source evidence.

Parent instance identity and liveness are separate three-valued observations. Unknown identity or liveness does not remove a possible worker-parent association; definite mismatching process-start evidence can exclude a historical instance. For several retained instances at one PID, every candidate must be disproved before that association is removed. A child still pointing at a reportedly dead parent remains contradictory evidence, while an explicitly bound child never becomes independent merely because its parent is unavailable. Current positive activity still needs fresh matched identity and a live process. Name inheritance likewise rechecks the old value against both previous and incoming trusted aliases, after the existing actor/namespace/chat gate; newly learned identity evidence cannot be ignored during inheritance. Real names, explicit clears, source-version fences and independent foreground precedence retain their existing rules.

## Cross-entry service and diagnostic contracts

Doctor preserves child exit status before public projection. A healthy JSON body
cannot override exit 1, spawn errors or signals. Exit 2 remains a supported
quality/live diagnostic result, but never establishes a healthy overall result;
a keychain-unavailable live probe retains separate local health evidence while
the overall doctor command remains nonzero.

Maintenance stops the LaunchAgent before checks that can rebuild `dist`, and
starts it only after all local checks pass. Failed stop prevents builds; failed
builds leave the service stopped. With `--no-restart`, local builds require a
confirmed absent job; loaded or unknown is rejected without stopping it.
`--no-restart --skip-local-checks` remains the diagnostic-only combination.
Public text/JSON exclude raw child output and allow only bounded diagnostic
vocabulary, numeric counts, exit status and a finding count.

Install captures the old plist and loaded state independently, validates staging
before stopping, and restores both after bootstrap/kickstart failure. Previously
unloaded configurations stay unloaded. Unknown inspection is never absence, and
a loaded job with no recoverable old plist is rejected. Rollback first confirms
the replacement is unloaded; restoring bytes alone cannot establish a restored
loaded configuration. Restoration and staging-cleanup failures remain explicit.

Synthetic regressions: `doctor-child-exit-contract.test.mjs` covers all three
children with misleading healthy JSON plus exit 1/2, error and signal outcomes;
`maintenance-boundaries.test.mjs` covers stop/build/start order, unloaded/loaded/
unknown inspection and public-output sentinels; `lark-im-install-rollback.test.mjs`
covers loaded/absent with existing/missing files, permissions, lint-before-stop,
rollback inspection/bootout/bootstrap/kickstart and cleanup failures. Existing
service start/stop/uninstall and independent foreground activity tests remain.

## Initial account association and bounded replay admission

The previous command-level sidecar publication required an entirely successful first command. A first `all` command could commit discovery and received facts after a sent failure, then permanently fall into legacy-unbound compatibility. A separate counterexample showed bounded replay ignoring a valid sidecar: another account could insert its own sent facts and make the original account conflict on its next normal sync.

New-source account reservation precedes runs; confirmation shares the first list/discovery transaction. Pending evidence blocks account changes without claiming successful collection. The sidecar remains compatible evidence, while a failed or interrupted publication cannot remove the database's association. Replay uses the same admission decision as sync. Synthetic regressions preserve both original public CLI sequences and test rollback, interruption, missing/corrupt binding evidence, and same-account/legacy controls.
