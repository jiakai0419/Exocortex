# Storage and entrypoint contracts

This describes the current Node candidate, not production acceptance. [Operations](operations.md) covers commands and maintenance; [Node reliability fixes](node-reliability-fixes.md) retains the original counterexamples. All test sources, identities, messages and databases are invented.

## Transactions and leases

### Sync account association (candidate)

Every Lark sync route, including discovery, resolves the current profile and checks the existing database association before changing records, runs, cursors or discovered scopes. A definite account conflict rejects the command before baseline changes as well. Invalid or unreadable binding evidence and a binding attached to a different database file also reject; they are not equivalent to a database that has never been bound. Schema initialization remains the explicit prerequisite needed to inspect a new database.

Compatibility is deliberately narrower than the remote sampler's positive-evidence requirement. A legacy database without a sidecar or usable sent-self evidence may continue syncing as unverified; it is not automatically rebound, its cursor is not reset, and no claim of historical ownership is made. Multiple received senders alone do not constitute a conflict. Sent-self evidence and the existing empty-database sidecar retain their current scope: account association, not tenant/app authentication or ownership of all history.

New empty sources reserve a hashed account association in `sources.config_json.initial_account_binding` after profile admission and before creating any run. The initial snapshot must be readable; a failed preflight cannot silently downgrade a new database to legacy compatibility. The reservation is made under a SQLite write transaction that rechecks the absence of records, runs, cursors, detail/list progress and active writers. A reservation is **pending**, not positive remote-sampling evidence: failed, skipped or interrupted work cannot claim a successful binding. Only the same account may retry it. Existing nonempty unbound sources retain the explicit legacy compatibility path and never receive a reservation from a current profile alone.

Confirmation time is no earlier than reservation time, even if the wall clock moves backwards during a command. Readers still reject evidence dated in the future; once the clock catches up the association becomes readable without manual repair.

Admission also requires the database file identity to remain unchanged from the initial snapshot through profile resolution. Replacing a legacy database with a fresh database during authentication must not apply the old database's compatibility decision to the replacement.

After admission, a fresh source first recovers stale locks belonging to its Lark scopes through the existing owner-aware recovery, unless an active maintenance lock is present. This preserves upgrade recovery when an older process died after taking its first lock but before creating a run or account reservation. The recovery is source-wide because the reservation is source-wide, but each call names an explicit Lark scope; other sources are untouched. Existing owner/lease comparison, live-owner protection and hard-lease rules remain in force, and the reservation transaction still rejects any remaining or newly acquired lock.

A complete list checkpoint (including durable detail debt) or an actual discovery commit confirms that reservation inside the same transaction as its effects. The source association therefore survives partial command success, process interruption after commit, and failure to publish the optional compatibility sidecar. No post-command success flag can erase that protection. Failed transactions and skipped discovery leave the reservation pending. Readers validate the embedded association, the existing sidecar and sent-self evidence together; corruption and contradictory accounts reject admission. Embedded evidence travels with the database contents, including a database-only backup/restore; it cannot become a stale sidecar attached to unrelated contents. Existing sidecars remain tied to their concrete database file, and a copied/replaced-file sidecar still rejects admission. A pending association stays unverified for remote sampling.

`sync` and `maintenance replay` use the same cross-process API lease and share the same account admission decision before any list/detail fetch or business write. Sync retains its command lease; replay acquires a non-waiting probe lease per request, inheriting it into the CLI child, and releases only after any shared cooldown publication. Both reject definite conflict and unavailable/invalid/replaced-file evidence; same-account pending retries and genuinely unbound legacy databases remain permitted. Replay does not silently bind legacy history. This is account association, not tenant/app authentication. It does not attest externally changed CLI credentials midway through a command.

Only a source confirmed empty with absent embedded association and absent sidecar may persist its initial baseline before profile resolution, preserving the intended start across a first-launch authentication failure and a retry after midnight. This baseline records collection intent and does not claim account ownership. Once saved, it survives later list failures and restarts. Existing history or account evidence requires account validation before baseline changes.

Synthetic acceptance must prove that a bound A-to-B switch leaves business tables, scope enablement, cursors and binding unchanged on every route; same-account work, multiple received senders and unbound legacy sources remain usable. Corrupt/replaced-file bindings, profile failure and first-discovery success/failure/skip require separate cases. Partial first success, interruption immediately before/after the first commit, failed sidecar publication, and replay through the public CLI require separate regressions. No real account, API or production database is needed for these checks.

Normal sync, discovery and detail completion share `runFenceGuardSql` and a **20-minute hard lease**. The fence executes inside the same write transaction as records, statistics, scope state and cursor effects. It checks the running run, source/scope identity, owner and acquisition timestamp, the transaction's SQLite clock, unchanged cursor, and enabled source/scope. An earlier JavaScript check is only an early exit; it cannot replace this guard.

Creating a run and acquiring its lock also require an enabled source/scope. A persisted initial baseline does not authorize a disabled source. Normal sync and bounded replay therefore share the same enable/disable boundary. If disable happens after fetch, writes fail atomically. `failRun` can close an otherwise valid owned run after disable, without saving records or advancing the cursor. Replaced owners, expired hard leases and changed cursors still reject it.

Lark list/detail transactions additionally check chat identity, progress generation, the list anchor and root fingerprint/version. They compose the common fence and record writer inside one transaction. Incomplete list pagination writes no progress. A complete list can save ordinary records and durable detail debt together, but missing detail content still blocks the full-content cursor. See [the list/detail contract](node-reliability-fixes.md#incomplete-details-and-bounded-progress).

The soft lock expiry, hard lease and process liveness are different evidence. None proves current activity; [Activity evidence](activity-evidence.md) requires a current phase and process identity. Maintenance enrichment uses a separate short lease, acquired only after remote lookups. Its shared helper checks owner, expiry and absence of sync locks inside the local write transaction, then performs CAS updates, counts effects and releases the owned lock. Dry runs and zero-change runs do not acquire that lock.

## Module ownership

Runtime consumers import the compiled facade `dist/storage/sqlite/ingestion-store.js` directly. Implementation modules depend on the small modules below, never back on the public facade. Explicit initialization lives in `src/storage/sqlite/initialize.ts`; its pre-schema initialization lock and permission setup are shared by initialization callers, not duplicated by the CLI.

| Module under `src/storage/sqlite` | Responsibility |
| --- | --- |
| `ingestion-store.ts` | Public facade, initialization/baseline and generic run lifecycle |
| `initialize.ts` | Explicit schema initialization with its pre-schema lock, private-path setup and restored umask |
| `maintenance.mjs` | Database checks, backup validation/ownership, run retention and compaction workflows |
| `ingestion-types.ts` | Shared internal record, scope and result types |
| `sqlite-executor.ts` | Quoting, JSON, private file permissions and one SQLite subprocess implementation; exec/query select output form |
| `sync-locks.ts` | Acquisition, recovery and maintenance owner/lease handling |
| `sync-run-fence.ts` | Common hard lease, run fence and cursor predicates |
| `record-storage.ts` | Batch normalization, version/identity checks, record SQL and effect counts |
| `lark-account-binding.ts` | Empty-source account reservation and transaction-composed confirmation |
| `lark-ingestion.ts` | Lark raw-root normalization, fingerprints, list/detail progress, generation checks and bounded replay transactions |
| `lark-name-projection.ts` | Lark-specific name inheritance and trusted alias checks |

SQL fragment helpers do not open nested transactions. Their caller composes guards and effects in a single write transaction. Generic runs for a second source neither read Lark progress tables nor inject Lark chat/list metadata. Name projection merging applies only when both source and record type are the Lark message type. This is a finite dispatch boundary, not a plugin framework.

Write-effect counts come only from the transaction that applies the version, identity and projection guards. There is no public preflight hash-only counter: a changed hash on an older revision is not an update, while a newer revision with the same hash can be. Callers use the effects returned by the commit operation.

The sync runner's injectable dependencies have the same finite keys and function contracts as its default implementations. Partial overrides remain supported; omitted dependencies retain their defaults. Command-level injected runners may implement only the requested scope's methods. Compile-time regression probes reject misspelled dependency keys, non-function overrides and invalid commit results at both entry points. This is a checked internal boundary, not runtime validation of arbitrary plugins.

SQLite reads through the write store retain its existing private-path behavior. Read-only diagnostics use `readonly-query.mjs`; consolidating subprocess code does not turn those reads into write-store calls.

### Read-only integrity evidence

Database checks and backup validation must detect actual CHECK-constraint violations, not only accept a mocked `quick_check` failure. SQLite can omit CHECK expressions when loading a read-only database schema, so a direct read-only `PRAGMA quick_check` is insufficient evidence. The integrity check restores a consistent snapshot through SQLite's backup API from an encoded `file:` URI with `mode=ro` into a private disk snapshot, then enables `query_only` and checks that snapshot. The source is never opened for writes; WAL frames are included by SQLite, and missing sources cannot be created. An exclusive 0700 directory and 0600 file keep temporary data private. Cleanup runs after success, query/restore failure and child timeout. Abrupt termination of the parent can leave that private temporary directory; it must not be committed or shared. This transient copy requires disk space proportional to the database and extra I/O, rather than retaining the whole snapshot in RAM. It is not a report, cache or retained backup.

Only one exact `ok` result establishes integrity. Restore, query, the 30-second child deadline or output failures stop validation; they cannot authorize backup publication or retention. SQLite's restore source retries an exclusive-lock conflict briefly; it does not inherit the destination connection's busy timeout. Other diagnostic queries retain their read-only connections. Regression tests use newly initialized synthetic schemas with deliberately invalid CHECK values, preserve source bytes and permissions, include committed WAL content, and prove that failed checks cannot displace an existing verified backup. The CI dependency probe exercises this same read-only-source snapshot path with a real constraint violation.

This consistent snapshot covers `quick_check` only. `databaseCheck` still reads other metadata and counts through separate source queries, so the entire report is not one atomic snapshot; replacing the source path between reads can mix observation times. Read-only WAL access may also update SHM reader coordination state without changing main-database or WAL contents.

Each database check, existing-backup verification or maintenance preview creates one temporary snapshot. Backup creation checks its source before and after acquiring the maintenance lock (two sequential copies), then validates its own newly created staging snapshot directly under `query_only`; that staging file is not copied again. Applied run retention and compaction each perform three sequential checks: before locking, under the lock and after mutation. This includes the worker's automatic retention every 1440 cycles even when no runs qualify for deletion, so its I/O and time also grow with database size. A failed post-mutation check reports failure but cannot undo an already committed mutation. `status`, `messages`, sync status and their lightweight queries do not use this path.

Only one integrity snapshot exists at a time per command, separately from the backup or compaction operation's own storage needs. Each snapshot restore and check has its own 30-second deadline, not a deadline for the whole maintenance command. The temporary target explicitly uses a 2 MiB page-cache target and allows cache spill. That is not a cap on total SQLite process memory or temporary disk use. Insufficient temporary storage fails validation and leaves existing backups intact. Cleanup removes only the exact directory created by the current call, never a scan of other users' or earlier runs' temporary files.

## Source versions

An adapter must declare whether a remote value is ordered. `encodeSourceVersion({ revision })` accepts an exact nonnegative integer as a decimal string, bigint or safe integer and returns canonical decimal text. `encodeSourceVersion({ token })` encodes an opaque string as `opaque:` followed by its JSON string representation. Numeric-looking tokens, whitespace and the empty token remain opaque and distinct. Preserve the original remote value in raw source content.

For compatibility, existing decimal `external_version` values remain ordered revisions; other stored strings are opaque. Revisions compare at arbitrary precision, without floating-point conversion. An older revision or a missing version cannot replace a known newer version. Equal versions can improve projections; bounded Lark replay retains its stricter newer-revision rule.

Different opaque tokens have no intrinsic order. Without an explicit predecessor, a different token cannot replace an existing one. For a source with an authoritative fetch, the adapter may first observe the stored version, then fetch the source, and supply the ephemeral `expected_external_version` hint:

| Hint | Guard in the same write transaction |
| --- | --- |
| Omitted | No predecessor assertion; ordinary version rules apply |
| `null` | No existing versioned record for this source and external identity |
| Stored version string | An existing record must still have exactly that stored version |

A matching string hint can authorize an unordered-token replacement only when both versions are nonnumeric. It cannot authorize numeric regression, erase a known version, change the record type, or move a record across sources. Failed CAS aborts the surrounding batch, including run/cursor/progress effects. The hint is not persisted in the record, canonical projection or raw payload. CAS proves absence of an intervening local replacement, not the ordering or freshness of remote tokens.

Ordinary writes without a CAS hint retain version-protected `record_type` replacement: equal or newer revisions, equal opaque tokens, and unversioned replacements can reclassify a record. Older revisions or different opaque tokens still cannot replace it. Batch normalization applies the same version selection without treating record type as globally immutable.

Explicit CAS candidates cannot repurpose a record's type. A batch with any CAS hint rejects conflicting types or predecessor hints for the same identity, so normalization cannot discard a CAS assertion. Different unordered versions in one batch are also rejected. Source plus external identity remains the database uniqueness key; adapters must choose external identities that are unique within their source. The record's first-seen scope must belong to that source. Type and predecessor guards for explicit CAS, and source/scope ownership for all writes, are checked inside the write transaction.

## Queries and entrypoints

Sync validates ISO-style `--end` calendar fields before acquiring its API lease, initializing storage or resolving an account. A leading `year-month-day` is checked independently of the remaining time syntax, including local times with repeated whitespace, non-padded clock fields or UTC/GMT suffixes. A nonexistent leading date or overflowing directly following clock field must not be normalized into a different synchronization window. Valid epoch-second, epoch-millisecond and local-time end values retain their existing interpretation. The explicit `--start` timezone and persisted modern-millisecond requirements remain separate; this CLI validation does not change remote message timestamp parsing.

`messages` and Lark quality queries explicitly require both `source_id = 'lark.im'` and `record_type = 'lark.im.message'`. The remote sample snapshot reads Lark records of any type so its comparator can report a conflicting type instead of treating it as a matching message. A different source or a different record type cannot be rendered as a Lark message or satisfy a sampled message lookup. Generic `sync-status` record totals intentionally aggregate all sources; those totals are not Lark message counts.

Transport, adapter detail classification and runner batch stopping use the same finite failure kinds. Exhausted transient failures include API internal-error codes 2200/1663 with their expected API envelope/message. Permission failures during detail retrieval become durable detail debt; they do not disable an otherwise readable scope. Only the list operation's supported permission evidence can disable that scope.

Service status aggregates recent failed runs with the same classifier and exposes only enum names and counts. Recognized permission evidence, including code 210508 and the supported permission messages, is `permission_denied`. Empty evidence and unrecognized public kinds remain `unknown` unless another supported signal establishes a classification. Known rate-limit, timeout, internal-error and scope-denial evidence retains its classification priority over fallback permission prose. Neither the JSON summary nor the terminal summary includes the original error text.

Lark two-stage runs record the result of each operation separately from full-content completion. A committed list is `succeeded`, even when it creates merge-forward detail debt. Store-generated `lark_progress` metadata identifies the `list` or `details` phase and `complete`, `awaiting_details`, or `attempt_failed` outcome, with this run's attempted/completed/failed counts and committed generation. A successful bounded detail batch can also await unattempted sibling tasks. Actual failed attempts, including responses rejected by stored-version protection, remain failed runs; pending debt alone is not an operation failure. Caller metadata cannot override this evidence. Only zero scope-wide pending debt promotes `cursor_after_json`, the scope full-content cursor and `last_success_run_id`, in the same fenced transaction as records, tasks and coverage metadata. A successful incomplete stage neither overwrites `last_error_run_id` nor supplies a coverage interval.

The exact internal `error_type=LarkDetailIncomplete` retains its public `detail_incomplete` classification. Older releases also used it for successful list transitions. Those original failed rows are never rewritten: diagnostics separately recognize a legacy list transition only when its strict phase/window/fence evidence matches a later retained detail run with atomic full-content closure, matching source, scope, scope configuration and cursor chain. Missing, malformed or over-budget proof stays unknown; a currently empty queue is not closure proof. Actual detail attempt failures never become normal transitions. Raw run/failure counts remain historical counts; default status excludes only proven resolved legacy list transitions from its problem count, while detailed output preserves their raw counts and resolution. Current pending debt and real failures remain visible. Public output excludes stored errors, metadata and private identities.

Coverage ignores valid successful `awaiting_details` stages without counting them as damaged success evidence, and still requires strict complete-window proof for coverage or remote sampling. Retention preserves awaiting or unverified stage evidence; completed no-op stages remain eligible under the existing age and current-success protections.

Status collects all database evidence in one read snapshot. Bounded run proofs cross the SQLite CLI boundary one run per JSON cell, avoiding the CLI's costly re-encoding of a large aggregate string. The reader validates unique run IDs and section limits before combining them; explicit empty sections remain distinguishable from missing evidence. This internal encoding does not change public report fields or the historical-proof budget.

Each legacy run's successor search inspects at most 101 candidates to detect the 100-candidate limit. Over-limit searches return unavailable proof without serializing their candidates to the CLI. A complete successor-proof array must also fit within 16 KiB of UTF-8 JSON; larger arrays return unavailable proof as a whole. Neither limit selects a convenient subset or truncates JSON to claim closure: the run remains unknown and actionable, even when an omitted candidate might close it.

Shared classification does not combine time budgets: a CLI subprocess defaults to 120 seconds, a request including retries to 180 seconds, a list window shares its own 180-second budget, and a queued detail attempt has at most 30 seconds. Only exhaustion of the list window's time budget permits bounded prefix shrinkage; internal errors and detail failures cannot trigger that path. Optional naming and single-chat metadata calls use a separate shared five-second request budget. Enrichment and bounded replay use the same transport with retries disabled and a command-wide maintenance request session: by default 12 actual CLI spawn attempts and 30 seconds of monotonic remote-work time, with at most five seconds per attempt. CLI internal HTTP fanout is not counted or promised bounded. A latched budget, lease or cooldown stop is checked before any local commit, even when optional resolvers catch the original failure. All replay scopes finish remote staging before the first scope commit; database-stage failures retain the existing per-scope transaction semantics. See operations for explicit bounds and precision limits.

Contact/member/application/bot lookup rules belong to the existing name resolver. Record enrichment consumes those rules and maps optional private observations into its existing diagnostics; scope enrichment consumes the adapter's single-chat metadata response. The two workflows retain distinct candidate selection and CAS updates. Exact `--names-only --record-id` selection restricts reads to named Lark records and writes to sender-name projections; it excludes system, cleared, known-name and inconsistent-identity candidates. Exact application fallback requires a matching app_id, never subset-derived uniqueness. Exact replay similarly filters a complete fetched window to explicit existing message IDs in one scope, includes the sorted target set in its plan hash, and checks original record ID, chat, creation time and known numeric version inside the replay transaction, alongside the predecessor version CAS, so deletion, replacement or same-version identity movement cannot turn repair into insertion or broaden the selected scope. An explicit application probe bypasses its positive cache, while failed refresh remains unknown and retryable. See [identity and projection](card-and-identity-projection.md) for the complete evidence contract.

Worker and service use one default/validation module with an explicit persistence whitelist. Adaptive options and the resolved database path can be installed in the long-running service; `--once` and `--max-cycles` cannot enter its plist. A `status --db` diagnostic override does not change that installed configuration. Steps, cycles and `check --wait` use the same injected observation clock in tests and the system clock by default. Service lifecycle and diagnostic exit semantics are documented in [Operations](operations.md).

Each ordinary worker step has a short-lived guardian and a private process-group anchor. The anchor stays alive until the guardian's one group-termination attempt, even after the step exits; its READY/GO/DONE control pipes are not inherited by the step. Step timeout, worker-parent exit and normal step completion all finish owned-group cleanup before accepting the step result. This covers an API request that outlives its sync parent while retaining the API flock descriptor. Requests continue to inherit the descriptor: releasing or deleting a live lock is not cleanup.

The guardian drains bounded stdout and stderr without blocking its monotonic deadline or parent checks, preserves the existing step JSON, transport summary, exit-code and partial-success contracts, and has a shared 100 MiB output ceiling. The sampling guardian's 60-second ceiling and cache protocol do not apply to ordinary steps. Cleanup sends one SIGKILL to the owned group and waits at most one second for its anchor; failed signalling is not retried or redirected to observed PIDs. The outer synchronous deadline sends SIGTERM to the detached guardian with cleanup grace. Fixed stage/errno diagnostics retain primary and cleanup failures separately, and either failure defeats successful or partial output.

This guarantee covers the owned group and a living guardian on the supported local POSIX host. It cannot promise cleanup after the guardian itself is forcibly killed, host failure, permission denial, or a descendant deliberately creating another session; these are not repaired by broad PID scans. Synthetic lifecycle regressions use fresh processes and private lock directories, prove exit and lock reacquisition before fixture fallback deadlines, and include caller TERM/KILL/group HUP, timeout, normal/partial exit with remaining descendants, and output pressure. No real API or service is involved.

Normal message preparation converts each message once. Equal-time/equal-ID candidates retain the previous received-before-sent ordering and stable order within each group, so a same-version duplicate still selects the same final record. The cursor probe recomputes count and order after filtering self messages. Filtered records retain their original page positions; the original-page summary and paging probes still describe the complete upstream page. Test fixture helpers share setup and read-only assertions, while individual synthetic counterexamples remain in their own suites.

## Verification boundaries

Regression suites include `ingestion-contracts.test.mjs`, `ingestion-source-contracts.test.mjs`, detail storage and replay, transport/adapter/runner, doctor child exits, service rollback, maintenance boundaries, worker options and cursor probes. They retain negative cases for rollback, stale owners, disable races, opaque CAS conflicts, numeric regression, incomplete content, error privacy and independent foreground work.

The full test command limits concurrent test files to four. Integration fixtures start real local child processes under the same five-second lookup deadlines as the application, so host CPU count must not multiply competing fixtures without a bound. Every test file and assertion still runs; production timeouts and retry policies are unchanged.

`npm run build:check` compiles into a newly created temporary directory, compares the complete output file set and bytes with `dist`, and removes its temporary output in `finally`. Missing declarations, stale content and orphan generated files fail the check, even when Git considers `dist` clean. The check does not repair or rewrite `dist`; ordinary `npm run build` does write it. `npm run verify` composes the required development checks without calling service lifecycle operations and belongs in an isolated checkout. The existing runtime maintenance recipe must stop the service before a build or test. History documents remain design records and link here rather than claiming to describe current behavior.

Local synthetic checks do not authorize account queries, production data changes, publication or deployment. Real sender lookup can remain unresolved when remote evidence is insufficient. The Node implementation remains in place; CLI v2 changes its entrypoints while preserving these storage contracts. See [CLI migration](cli-migration.md) for retirement gates and behavior differences.
