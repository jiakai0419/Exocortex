# Shared cooldown publication

The existing writer creates a hard link to a completed temporary file, then removes the temporary name. Between these operations the visible final inode has two links. The private JSON reader correctly rejects such an inode, so another valid publisher can lose its larger reset when its preflight returns unavailable. A deterministic two-process synthetic interleaving reproduces this defect; a successful ordinary rerun does not remove it.

Publication must expose a fully written, single-link immutable record in one filesystem operation. The candidate creates a private temporary directory containing only `value.json`, writes and fsyncs that private single-link payload, closes it, then atomically renames the complete directory to `operation-expiry.json` in the same private parent. Different expiries retain different final names. A valid same-expiry final directory is nonempty, so another directory rename cannot replace it; the competing writer validates the winner and removes its own temporary directory. A legacy final file cannot be replaced by a directory rename either. The payload and directory ownership, modes and stable metadata remain the trust boundary.

The reader accepts both legacy files and complete private directories at the same final name. Directories must contain exactly `value.json` and retain the same identity and metadata across the read. The payload still requires private ownership and mode, one hard link, a bounded stable descriptor read, supported operation, valid expiry, and matching versioned content. Expired directories first move atomically out of the published namespace into a private temporary name, then only their known payload and empty directory are removed. There is no recursive deletion of unknown entries.

Temporary cleanup requires captured object identities, not merely a currently private path. The writer captures the newly created directory and its exclusively created payload descriptor. Retirement captures the validated expired directory and payload, together with its separately created empty destination. Cleanup may use the captured empty destination if rename did not occur, or the captured expired source if it moved there; this also handles a reported error after the actual rename. It compares device, inode, birth time, type, owner and mode, requires a single-link payload, rejects aliases and unknown children, verifies the payload identity before unlink, and verifies the directory identity again before removing the empty directory. A different same-owner private directory, replaced payload or unknown child is retained rather than deleted. Failed creation never acquires cleanup ownership. Directory timestamps/link count legitimately change when its payload is created, deleted or moved (including ordinary-file entries on APFS); stable content reads remain stricter. These are bounded path-identity checks, not a claim that path lookup and unlink become one atomic operation against an adversarial same-user filesystem mutator.

Existing larger shared evidence can satisfy a smaller or equal write without publishing another entry. Same-expiry concurrent writers occupy one final entry, including eight simultaneous publishers with 127 records already present. An earlier nonce-file prototype was rejected because it multiplied same-expiry entries and could exceed the cap. There is no new remote request, retry loop, timeout, API lease or daemon. The existing 128-record admission guard and 512-byte read cap remain. Concurrent distinct expiries can already race the admission guard on the base; this patch does not claim to solve that separate capacity limit.

Older binaries reject directory records and fail closed, including after expiry: their preflight cannot clean an unrecognized record. A rollback must therefore not simply restore old code and expect automatic recovery, or delete still-valid cooldown evidence. Before any release using this format, its release owner must provide a separately verified legacy conversion or retain a compatible coordinator in the rollback plan. This patch does not silently perform a production conversion.

A safe conversion protocol requires all writers quiescent and the shared API lease held, validates every source record, then creates an exclusively owned private marker whose deliberately unrecognized filename makes both old and new readers fail closed. With that blocker retained, it stages and fsyncs equivalent legacy files, retires each directory, and atomically publishes the corresponding legacy file. Before removing only its exact owned blocker it verifies all operation/global maximum resets and ownership checks are unchanged and no new-format records remain. Failure or interruption leaves the blocker and conversion journal for explicit recovery, rather than permitting an API request without the prior cooldown. A source conflict, unknown entry or failed validation stops conversion. This is a required deployment design boundary, not an implemented automatic recovery tool or current production action.

Required verification uses actual product functions and independent synthetic processes: a reader and longer publisher paused at the publication boundary, same-expiry and different-expiry concurrent writers, the near-cap publication barrier, legacy reads, partial-publication failure and cleanup, and hostile hardlink, symlink, FIFO, malformed-name and permission controls. Both staging and retirement additionally cover different private directory and payload substitution, unknown children, rename errors before and after execution, and directory replacement after payload unlink but before rmdir. Reader security checks and the original maximum-reset assertion must not be weakened to make concurrency pass. All files and timestamps are invented; no production coordination directory or API is used.
